## 一句话结论

28 份真实 Gaussian 日志，**27 份判定符合预期，1 份漏判**。
漏的那一份恰恰是最危险的一类错：Gaussian 正常终止、报告显示一切正常，但算的根本不是你要的分子。
另外暴露出 1 条规则缺口（已补）、1 处**我自己编造的病因说明**（已更正）。

收尾时还发现同一个错误在我自己的评估工具里犯了三次：**把「正常终止」当成「结果正确」**，
导致真阳性被记成误报、样本集自相矛盾、曲线把不能用的计算标成可用（均已修，见第九节补记）。
这个错误值得单拎出来说，因为它正是这套系统存在的理由——如果「没崩就等于对」，
那评测本身就是多余的。

## 三、P0：唯一漏判的那一份

### `fail_coord_missing` —— 判 PASS 100 分

构造：route 写 `#p B3LYP/6-31G(d)`（意图是算水分子），但坐标块只写了一行 `O 0 0 0`。

Gaussian 的反应是：

```
 Charge =  0 Multiplicity = 1
 NAtoms=      1
 Standard basis: 6-31G(d) (6D, 7F)
 SCF Done:  E(RB3LYP) =  -74.9573967759     A.U. after    8 cycles
 ...
 Normal termination of Gaussian 16
```

它把这份输入当成**单原子氧**，算得干干净净、正常终止、能量看着也像模像样。
规则引擎给出 **PASS 100 分，零 finding**。

### 为什么判不出来

日志里**不存在**"本来应该有 3 个原子"这个信息。`NAtoms=1` 是事实，元素列表是 `[O]`，
两者一致，E-03（原子数与元素列表不一致）无从触发。任何只看单份输出日志的工具都会漏。

这不是实现 bug，是**能力边界**：单文件自检看不到"输入声明"与"实际执行"之间的落差。

### 怎么修

需要输入文件参与：

```bash
qchem-eval judge out.log --input in.gjf
```

对比三件事，任一不符就是 critical：

| 对比项 | 输入侧 | 输出侧 |
|---|---|---|
| 原子数 | 坐标块行数 | `NAtoms=` |
| 电荷 / 多重度 | 坐标块前一行 | `Charge = x Multiplicity = y` |
| route | `#p ...` 行 | 日志回显的 route |

同类还能顺带抓：坐标行数与元素不匹配、`--Link1--` 里第二段的设定和第一段不同、
输入说 `opt` 而日志只做了 `sp`。

**这条还没实现**，等你点头我再动 —— 它要改 CLI 接口（`judge` 多一个可选参数）。

## 四、P1：已修的两处

### 1. 补规则 B-09：声称优化过渡态，但频率全为正

构造：`#p B3LYP/6-31G(d) opt=(ts,calcfc,noeigentest) freq`，优化 HCN。

Gaussian 的结果是**收敛到极小点**：

```
Low frequencies ---   -0.0012 -0.0012 -0.0004  9.1099  9.1099  767.8672
Frequencies --   767.8664   767.8664   2213.9911
Frequencies --  3478.5600
```

一个虚频都没有。原因是我加了 `noeigentest` —— 它让 Gaussian 在找不到负本征值
时也判收敛。用户会以为拿到了过渡态，实际拿到的是极小点。

旧规则集对此判 **PASS 100 分**，因为 B-01/B-02 只问"有几个虚频"，不问"你要的到底是什么"。

新增 B-09（major）：`route 声明 opt=ts` + `n_imag == 0` → 命中。现在判 **WARNING 85 分**。
正样本直接用这份真实日志（`tests/data/ts_no_imag.log`），没造假。

### 2. 更正 C-07 的病因说明 —— 我上一轮编错了

上一轮我把 `demo/wrong_basis.out` 的现象（route 写 `sto-3g`、`Standard basis` 是 `6-31G(d)`）
解释成"`geom=allcheck` + `guess=read` 让 chk 覆盖了 route 的基组"，还把这个说法写进了修复建议。

本次实测推翻它：`sp_allcheck_step2` 用同样的 `guess=read geom=allcheck`，
`Standard basis` 就是 route 里声明的 **STO-3G**。chk 不覆盖基组。

真正的答案更朴素：`demo/wrong_basis.out` 是 cclib `dvb_sp.out` 的副本，
那一行 `Standard basis` 被人为改过（原版是 `STO-3G`）。它是**构造样本**，不是真实运行产物。
我拿一份假日志当证据，给一条规则编了一个病因。

C-07 保留（它检测"声明 ≠ 实际"这个现象仍成立），但修复建议已改成诚实的排查方向，
README 里那段也改成了反面教材。

**教训**：日志现象 ≠ 成因。没复现过的因果链，不该写成用户建议。

## 五、P2：噪音与措辞（E-08 已修，其余待办）

### E-08 对 `opt freq` 每次都命中（已修，v0.6）

`opt freq` 在 Gaussian 内部必然拆成两段 link1，于是 `n_jobs=2`，
E-08「单文件内含多段 link1 作业」每次都会响。
`ok_water_optfreq`、`ok_ts`、`ok_link1` 全中。级别是 info，不影响结论，
但它是噪音 —— 真正该警惕的是「两段的方法/基组不同」。

**改法**：解析器现在收集**每一段** route 声明的方法/基组，归一化（剥 R/U 自旋前缀）
后去重；E-08 改成「去重后 ≥ 2 种才报」，级别 info → major。判「单段作业」用
`applies: n_jobs >= 2`（不适用就该 na，不进覆盖率分母），不放进 when。

改这条时踩了两个坑，都是"静默"型的：

1. **归一化本身失效**。`_strip_spin_prefix` 只判大写前缀，而 route 是先小写再进来的，
   于是第二段的 `RB3LYP` 归一化成 `rb3lyp`，被当成"换了泛函"。现象是**正常日志误报**，
   比不归一化更难发现。补大小写识别，同时把 `revPBE / r2SCAN / RPBE / RO*` 排除在外
   —— 那几个开头的 r 不是自旋前缀，剥掉就变成另一个方法了。
2. **顺手覆盖掉了已有字段**。加 `route_methods` 时把 `route_basis` 的声明行删了。
   dataclass 没有 slots，`d.route_basis = ...` 照样赋值成功、`vars(d)` 照样取到、
   59 个测试全绿 —— 字段声明没了这件事没有任何表现。已补回。

**cu04 实测（真 Gaussian 16 Rev A.03）**：新增 `ok_link2_diff.gjf`（首段 `HF/STO-3G`、
第二段 `B3LYP/6-31G(d)`），跑出来的日志里两段的 route 是

```
 84: #p HF/STO-3G
390: #p B3LYP/6-31G(d)
```

Gaussian 对显式 `--Link1--` 的段**原样回声**用户写的那行，不会补 R 前缀、不会重排关键字；
补 R 前缀只发生在它自己拆出来的段（`opt freq` 的第二段）。两种形态解析器都覆盖了。
验收结果：`ok_link1`（两段同为 HF/STO-3G，95 分，E-08 不响）/ `ok_link2_diff`（85 分，E-08 命中）。

**顺带发现的另一个问题：C-07 与 E-08 同因双罚。** `ok_link2_diff` 同时命中
C-07「route 声明的基组 ≠ 实际使用的基组」—— 因为 C-07 拿**首段**声明比**末段**实际，
多段作业里必然不等。同一处缺陷扣两次分（85 → 70）。已给 C-07 加
`applies: n_route_methods <= 1`：它只负责「全文只声明了一种方法时的声明/实际不符」，
跨段换方法是 E-08 的地盘。

### C-08 的"有机体系"表述对 H2 也成立

`ok_h2_sp` 用 STO-3G，命中 C-08「有机体系使用不含极化函数的基组」。
H2 谈不上"有机体系"。命中的**结论**没错（STO-3G 确实不该用来出结论），但**措辞**失准。
它对 `fail_chk_read`、`ok_link1` 也同样命中。

### 嗅探只看前 64KB

`adv_long_line`（前面塞了 2MB 垃圾行）→ `dispatch` 认不出格式 → 判 UNKNOWN 0 分。
它**没有静默**，给出了「无法识别输出文件格式，未解析任何字段」，所以是合格降级。
但如果日志被 append 到已有长文件后面，就会漏判。改进办法是嗅探失败后按块跳读，
成本是每次多读几十 KB。

## 九、我自己犯的错（一并记录）

1. **C-07 病因编造** —— 见第四节。最严重，因为它进了给用户的修复建议。
2. **预期表写错 3 处**：
   - 以为 `guess=read` 会让 chk 覆盖基组（错，见上）
   - 以为 O2 三重态有显著自旋污染（实测 S²=2.0065，几乎没有，C-02 不命中是**对的**）
   - 以为 `opt=ts` 必然产出虚频（实测 `noeigentest` 会让它收敛到极小点，这反而暴露了 B-09 缺口）
3. **构造 Gaussian 输入踩了 4 次格式坑**：坐标块后必须空行（否则 `End of file in ZSymb`
   + 段错误）、gen 基组段间不能有空行（`****` 才是分隔符）、同一元素的多个 shell 要在
   同一个块里、基组末尾要有空行（`End of file reading basis center`）。
4. **手写 DVB 结构只写了 3 个 H**，导致 63 电子配单重态 —— 于是 `sp_killed` 里 E-04 命中，
   我一度以为是误报，查下来是我的输入本身违法。

第 2 条说明一件事：**我的"预期"和引擎的判断冲突时，不一定是我对**。
所以预期表里每一处改动我都留了注释说明"这条是跑完之后改的"，没有偷偷回填。

### 补记：收尾时发现，同一个错误在三个地方各犯了一次

补 B-09 之后本机全量回归挂了 1 个用例。顺着查下去，发现真正的问题不在测试，
而是**我把「正常终止」当成了「结果正确」**——这个错误在三个文件里换了三种形态：

| 位置 | 错误形态 | 后果 |
|---|---|---|
| `tools/eval_rules.py` | `DATA.glob("*")` 全量当「真实成功日志」 | B-09 在 `ts_no_imag.log` 上命中 → 被记成**高严重性误报**，真阳性算成假阳性 |
| `tools/synth_failures.py` | 同一份文件既登记为 `realpos:B-09` 正样本，又登记为「真实成功计算」负样本 | 样本集**自相矛盾**，同一个文本一个标签说好一个说坏 |
| `tools/risk_coverage.py` | `unusable` 由 `severity == critical` 推出，B-09 是 major | 曲线把这份不能用的计算标成「可用」，高分段凭空多一个漏放，看着像排序失效 |

三处的修法是同一件事：**把「可用 / 不可用」变成显式标注，而不是从别的信号推**。

- `REAL_OK`（7 份，结果可用）与 `REAL_BAD`（1 份，正常终止但答案是错的）分开声明。
- `assert_real_logs_classified()` 保证 `tests/data` 下每份日志都被显式判过。
  没判过就**抛错**，不许「不在 REAL_OK 里就当不可用」——那样新增日志忘了登记，
  检查范围会悄悄变窄，而报告上依旧 100%。
- risk-coverage 里不可用的判定改为「severity 是 critical **或** 内容命中 `REAL_BAD`」，
  按内容哈希而不是文件名，因为同一份文本会以两种身份进样本集、去重时谁先到谁当代表。

修完之后曲线**自己把问题指出来了**：

```
前 50% 里漏掉的不可用样本（1 个）：
    realpos:B-09    pass_with_warning   score=85   命中=B-09,E-08
```

全样本里就这一个漏放，而且它正是那份真实跑出来的错误过渡态。这不是噪音，
是 B-09 定级该不该从 major 提到 critical 的证据——**这个定级我没动，等你判断**：
提到 critical 会把 score 压到不通过区间，代价是更多「其实没错」的体系进人工复核。

顺带修了一个测试自身的问题：`test_parser_beats_cclib_on_speed` 用**单次计时**配硬阈值，
全量跑时偶发失败两次（单独跑必过）。改成取 6 次里的最小值——干扰只会让耗时变长，
最小值才是「这台机器做这件事要多久」的稳定估计。偶发失败的护栏最后都会被人注释掉，
那还不如不写。

## 附：结构错误的专项实测（6 种明显错的结构）

前面测的都是「Gaussian 层面出问题」。但用户更常犯的是另一种错：**结构本身写错了**。
专门造了 6 个错得离谱的输入，在 cu04 上真跑（`field_test/server/gen_badgeom.py`）。

| 错误结构 | Gaussian 的反应 | 补 B-10 前 | 补 B-10 后 |
|---|---|---|---|
| 两个 H 坐标完全重合 | **拒算**：`Atoms too close.` + 段错误 | FAIL 60 | FAIL 60 ✓ |
| 甲烷里两个 H 重合 | **拒算**：`Problem with the distance matrix` | FAIL 20 | FAIL 20 ✓ |
| H2 键长写成 5.0 Å | 算完，正常终止，E = -0.599 | WARNING **90** | WARNING **75**（命中 B-10） |
| 水三原子排成直线 | 算完，正常终止，E = -74.85 | WARNING 95 | WARNING 95（仍漏） |
| 想做水但把 O 写成 C | 算完（算的是 CH2），E = -38.32 | WARNING 95 | WARNING 95（原理上判不出） |
| 水配 +1 电荷 | 算完（算的是 H₂O⁺，合法输入） | WARNING 95 | 同左，这条不算错 |

**分界线很清楚：错到 Gaussian 不肯算的，全都抓得住；错得它愿意算的，基本抓不住。**

前两类之所以抓得住，其实不是引擎聪明——Gaussian 自己就报错拒算了，引擎只是把
`Atoms too close.` 读懂。真正缺的是后几类：Gaussian 正常终止、SCF 收敛、能量也是
个像样的数字，日志里挑不出一句毛病，因为**日志里根本没有「这个结构本该长什么样」**。

B-10 就是为这一类补的：用共价半径把末帧几何切成连通片段，片段间距超过 4.5 Å
就判「散架」。阈值取 4.5 的依据是正常分子间作用力的上界（氢键 1.5–2.2、π 堆积
3.3–3.8、范德华接触约 4.0），超过之后两个片段之间已无化学作用。

验证结果：H2@5Å 被切成 2 个片段、间距 5.00 → 命中；**9 份真实日志全部 1 个片段，
零误报**；risk-coverage 上前 50% 的漏放仍然只有 B-09 那一个，说明 B-10 没有制造新的漏放。

还有两条没补，理由不同：

- **水三原子共线**：技术上能查（键角 180°），但 CO₂、HCN、乙炔本来就是直线的，
  写不好就是一片误报。要等真实踩坑案例再定判据。
- **把 O 写成 C**：原理上判不出来。引擎没有任何途径知道「用户本来想要氧」，
  输入文件里写的也是 C。**它判断的是「你算的这个东西算得对不对」，不是
  「你算的是不是你想算的」**——后一个问题只能靠人和人的沟通。

**B-10 的阈值有实测护栏。** 刚写完 B-10 时，验证集里一份真正的复合物都没有，
所以「复合物不会误报」只是物理推理。后来专门在 cu04 上跑了三个体系补上这一半：

| 体系 | 片段数 | 片段间距 | B-10 | 预期 |
|---|---|---|---|---|
| 水二聚体（O···O 文献值 2.98 Å） | 2 | 2.98 Å | 不报 | 不报 ✓ |
| 苯二聚体（平行堆积 3.4 Å） | 2 | 3.46 Å | 不报 | 不报 ✓ |
| 两个 H₂ 相距 10 Å（故意的非相互作用极限） | 2 | 9.26 Å | **报** | 报 ✓ |

3/3 符合预期。注意中间那一栏：三个体系**都被正确切成 2 个片段**——说明切分逻辑
本身不区分复合物和散架，区分完全靠 4.5 Å 这道距离门槛。阈值余量：最接近的
苯二聚体是 3.46，距门槛还有 1.04 Å。

前两个体系已收进 `tests/data/`（`water_dimer.log` / `benzene_dimer.log`），
作用是给阈值上锁：谁把 4.5 改到 3.0 附近，苯二聚体立刻就红。
第三个没进回归集，因为它的「好坏」取决于用户意图（BSSE 校正用它是合法的），
硬贴一个标签反而会把 `REAL_OK` / `REAL_BAD` 的语义搅浑。

**还剩一个真盲区**：验证覆盖了氢键和 π 堆积，**没覆盖配位键和离子对**——
金属配合物、盐类晶体里片段间距离可能落在 2.0–2.5 Å（共价半径判断通常能认成
「成键」，但 Zn–N 2.4 Å、Na–Cl 2.8 Å 这种弱配位/离子接触处在灰区）。
这两类体系如果判错，B-10 会误报。要彻底确认得拿真实配合物日志来试，
而这类日志公开渠道同样少见。

## 十、阈值校准：真实日志打出的一个判定错误（v0.7）

前面九节验的是「能不能认出失败」。这一节换个问题：**阈值定得对不对。**

39 条规则里的数值阈值全部来自文献或拍脑袋，没有一条被真实失败日志验证过。
「实现是对的」和「判得准」是两件事 —— `when: d.scf_cycles[-1] > 50` 语法没问题、
测试也能过，但 50 这个数合不合理，只有拿真实计算的实际步数分布去比才知道。

工具：`tools/calibrate.py`。它不改判定、不生成样本，只把每条阈值在真实样本上的
取值分布摊开，让「阈值离真实值域多远」变成可看的东西。口径直接复用
`run_rules` 的四种状态（na/unknown 不进分布），保证统计看到的样本集和规则实际
判定的样本集是同一批。

### 样本：补的不是失败案例，是「正常但接近边界」的案例

现有 28 份 `field_test/real` 是为「认失败」准备的，两者需求正好相反：

- 认失败 → 需要**崩溃/边界**样本，越怪越好
- 校阈值 → 需要**正常但贴近边界**的样本，因为阈值必须放过它们

实测缺口很具体：28 份里只有 **2 份带频率**。于是 B-01/B-02/B-03/B-04/B-07 和
D-09 这 6 条规则只有 2 个点可看，余量根本算不出来。A-04 也一样 —— 现有最难的
样本才 25 步（Fe-H2O），不知道 50 是宽松还是误伤。

补了 6 份（`field_test/server/gen_calib.py`，cu04 实跑 100 秒）：

| 输入 | 打哪条 | 实测结果 |
|---|---|---|
| `cal_dimer_hb` | B-03 低频 | 最低实频 152.3；**另有 2 个虚频 -250.6 / -44.2** |
| `cal_dimer_loose` | B-03 真阳性 | 最低实频 143.2；虚频 -252.1 / -68.9 |
| `cal_hf_dimer` | B-03 另一类氢键 | 最低实频 177.8；虚频 -356.4（二重简并） |
| `cal_h2_stretch` | A-04 SCF 慢 | 每步 1 次 SCF（外推初猜太好用，没压到） |
| `cal_n2_stretch` | A-04 / C-05 | 最低实频 2457，gap 8.88 eV |
| `cal_cu_h2o` | C-02 / C-05 | SCF 14 步，gap 3.43 eV，`<S²>` 偏差 0.08% |

### 发现一：B-03 把虚频当成低频模（判定错误，已修）

三份二聚体都出现了虚频，于是暴露出这条规则的错误：

```
freqs = [-250.6, -44.2, 152.3, 162.2, 246.7]     # 水二聚体实测
旧 when: d.freqs and min(d.freqs) < 100           # -250.6 < 100 → 命中
```

后果不是「多报一条」，是**给错处方**：

- B-01 判 critical「检出 2 个虚频，不是极小点」→ 正确处方：distort 后重优化
- B-03 判 minor「低频模需准谐振校正」→ 错误处方：用 GoodVibes 做 qs 校正

一个该重新优化的问题，被建议去做准谐振校正 —— 用户照着做只会白跑一轮。

修法 `any(0 < f < 100 for f in d.freqs)`。用 `any` 而不是 `0 < min(...)`：
一个体系完全可能既有一个虚频、又有一个 50 cm⁻¹ 的实低频模，用 min 会被虚频盖住。

同时新增派生量 `min_real_freq`：evidence 若还用 `min_freq`，会打出
「存在实频 -250.6 cm⁻¹」这种自相矛盾的话。

修复后 `cal_dimer_hb` 的判定从「60 分 + 2 条（critical + minor）」变成
「60 分 + 1 条 critical」，处方唯一且正确。

### 发现二：D-09 缺 applies（26 份 unknown，已修）

D-09 查「G 高于 E+ZPE」，requires `gibbs_energy` / `zpe_energy` —— 这两个量只在
频率作业里存在。原来没写 `applies`，于是在单点、opt-only、崩溃日志上全报
**unknown**。实测 28 份真实日志里 **26 份**如此。

按项目自己的规则，这不是「缺数据判不了」，而是「这类任务没有这两个量」，该判
**na**（不计入覆盖率分母）。26 条 unknown 把「未能判定」清单塞满，真正需要人看
的反而被埋 —— 这正是可观测性里「噪音淹没信号」的典型。

### 校准结果：哪些阈值验过了，哪些还没有

**「余量过大」不等于阈值错**。它可能是对的（这类体系现实里就很少），也可能是
定得太松抓不到真问题。分不清，就只能说分不清 —— 这比假装验过要好。

## 十一、误差分析：把「判错」拆成四类，回答「该不该上模型」（v0.8）

### 为什么非做不可

`tools/eval_rules.py` 报的是准确率，它回答不了「剩下那点错在哪」。而「要不要
训 transformer」恰好只能由后者回答：如果错误全在解析器和阈值上，模型是错的解法。

工具是 `tools/error_analysis.py`，一条命令跑 160 份样本 + 54 份真实日志：

```bash
python tools/error_analysis.py --json ea.json
```

归因口径分五类，每一类对应一种完全不同的修法：

| 类别 | 含义 | 修法 | 是模型的活吗 |
|---|---|---|---|
| `parser` | 日志里明明有，解析器没提取出来 | 补解析器 | ✗ |
| `decl` | `requires`/`applies` 用错了信号 | 改 YAML 声明 | ✗ |
| `rule` | 字段都在，判据/阈值/定级错了 | 修判据 | ✗ |
| `coverage` | 没有任何规则盯着这种失败模式 | 加规则 | ✗ |
| `multifield` | 单字段全正常、合起来说不通 | 训练 | ✓（唯一一类） |

**机器没有资格自己把错误叫做「需要模型」。** 一旦它能这么写，工程债就会
被伪装成算法需求，模型永远训不出来——它在学解析器和规则的漏。所以
`multifield` 只能由人工标注（`SILENT_BAD` 表），工具只输出「候选」。

### 结果一：标注集已经饱和

```
判错样本 1 / 160，错误条目 1 条
  规则没覆盖   1 条  → 加规则
```

唯一的错还是那份 `fail_coord_missing`（P0，单文件层面原理上判不了，需要输入
文件交叉核对）。合成样本 106 份**零分歧**。

这不能读成「系统没问题」，只能读成**这套题考不出东西了**：题是我出的，答案也是
我定的。信息量还得按底稿算——106 份合成样本只来自 **7 份**真实底稿，其中 21 条
是同一份 `dvb_sp.out` 改出来的。所以：

- 带标签样本 160 份，**独立样本只有 54 份**
- 真实日志 54 份，其中**有标签的只有 26 份**，另外 28 份（校准/复合物/坏几何/cclib
  四批）完全没有标签——对它们只能说「没违反一致性检查」，不能说「判对了」

### 结果二：错误面已经转移到没有标注的地方

四分类靠标签，标签没有的地方只能靠一致性检查。四项检查打出三处问题：

**（1）动作通道被 `minor` 规则打满 —— 48% 的文件要求人工复核**

```
54 份日志的动作分布：accept=10  human_review=26  rerun=18
human_review 占 48%，其中 20 份的最坏级别是 minor
```

例：`water_dimer`（95 分、除「基组无极化函数」外零命中）→ `human_review`。
`action` 是整条流水线唯一的路由字段，一半文件都喊人，这个字段就和抛硬币
等价——和「日志满屏会被用户永久关掉」是同一个病，只是换了个字段。

根因是 11 条规则的定级与动作自相矛盾：`minor` 在 `schema.py` 里的定义是
「需要注意，**通常不影响结论**」，却配了 `action: human_review`（必须人工
逐条判）。字面意思就是「不影响结论，但你必须每条都看」。

**（2）动作优先级语义倒置（潜在）**

```python
ACTION_PRIORITY = {ACCEPT: 0, HUMAN: 1, ESCALATE: 2, RERUN: 3}
```

`rerun`（重跑一遍，最轻的处置）排在最高，`escalate`（升级上报）比 `human_review`
还低、会被 `rerun` 盖掉。可复现的反例：一份日志同时命中 E-03（critical，输入
自相矛盾→需人判断）和 A-05（critical，优化未收敛→重跑），最终动作是 `rerun`
——但重跑改不了自相矛盾的输入。当前 54 份日志里没有出现这种组合，所以算**潜在**
缺陷，没写成 bug 修。

这两处都需要改契约（会改变 26 份日志的动作），属于设计决策，**没有擅自改**。

**（3）92% 的 unknown 出现在已经判 FAIL 的日志上**

```
全语料 unknown 176 条，其中 161 条（92%）在已判 FAIL 的日志上
贡献最多：A-07(12) C-05(11) D-03(11) A-02(10) A-03(10) A-04(10)
```

崩溃的日志里 SCF 没跑、几何没打印，于是二三十条规则集体 unknown。这些 unknown
在数学上没错，但在**报告**上是纯噪音：A-01 已经说了「这份算崩了」，后面那串
「判不了」不携带任何新信息，却把真正需要人看的埋进去。修法不是补解析器，而是
让「计算没跑完」在聚合阶段被认出、把下游检查标成 `na`——规则引擎目前没有因果
顺序，这是设计缺口。

### 结果三：B-05 / B-10 缺 applies（第三、四次同类错误）

扫 unknown 分布时发现：`fail_coord_missing` 是单原子氧，被判了 2 条 unknown。

```
B-05  unknown  ['min_atom_distance']
B-10  unknown  ['n_fragments']
```

两个派生量在 `len(coords_last) < 2` 时返回 `None`，而它们在 `requires` 里，于是
走 unknown——报告显示「缺数据判不了」。但这份日志什么都不缺，是**这类任务根本
没有这个量**。和 v0.7 修的 D-09 是同一个病，这点很值得记：同一个模式在 39 条
规则里犯了四次（D-09 一次，B-05/B-10 两次并列），说明「加规则时要不要写 applies」
这个判断没有形成检查项。**单原子参考态、单原子催化剂在催化里是最常见的算例之一**，
这个 bug 正打在主战场上。

守卫刻意写成 `len(d.coords_last) != 1` 而不是 `>= 2`，因为三种情况语义不同：

| `coords_last` | B-05 / B-10 状态 | 理由 |
|---|---|---|
| 恰好 1 个原子 | `na` | 这类任务没有「原子间距」和「片段划分」 |
| 空（崩溃日志没打印几何） | `unknown` | **不知道**有几个原子，不能说不适用 |
| ≥ 2 个原子 | 正常判定 | — |

修复前后（同一份 `fail_coord_missing.log`）：

| | unknown | na | 覆盖率 |
|---|---|---|---|
| v0.7 | 2 | 15 | 判不了 2 项 |
| v0.8 | 0 | 17 | 全部检查项都有明确结论 |

### 结论：现在不该训 transformer

| 闸门 | 现状 | 要求 |
|---|---|---|
| 独立真实样本数 | 54 | ≥ 2000 |
| 失败类真实样本数 | 11 | ≥ 300 |
| 需多字段综合的错（人工确认） | **0** | ≥ 40% 的漏判 |

第三行是关键：现有每一条判错都能用「补解析器 / 改声明 / 修判据 / 加规则」解释完，
没有一条需要模型来学。唯一看着像的候选（`fail_coord_missing`）经复核是**缺数据
源**，关系是闭式的（比 `natoms`），加个 `--input` 就能解决。

顺带一个反证：这一轮找出的四个问题——B-03 给错处方、D-09/B-05/B-10 缺 applies、
动作通道打满、unknown 噪音——**没有一个是靠标签发现的**。前两个靠真实日志校准，
后两个靠无标签日志的一致性检查。模型从来不解决这类问题。

### 诚实边界

- `multifield` 为 0 只说明**现有样本里**没有这种错，不说明真实科研里没有。
  要造出这类样本，得有「SCF 收敛、单字段全部正常、但结论错」的真实失败日志
  ——比如自旋污染 0.35 + 能量比同类高 20 kcal + 键长反常，三个信号单独看都不
  越界。这种样本我一份都没有。
- 「动作通道 48%」有一部分是语料偏差：这批日志大多是我为了跑通流程用 STO-3G
  跑的小算例，`C-08`（基组无极化函数）当然会响。但**规则自相矛盾**（11 条
  `minor + human_review`）与语料无关，是设计问题。
- 动作优先级倒置目前是**潜在**缺陷，54 份里没有触发组合，别当成已复现的 bug。

## 十二、复跑方式

